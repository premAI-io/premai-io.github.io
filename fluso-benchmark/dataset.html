What is inside the benchmark

This page explains the test set in plain language: what kinds of work appear, how the suite is grounded, and how to interpret the task mix.

The current suite contains 93 benchmark cases across 9 task families. The goal is to cover the kinds of work that matter in day-to-day knowledge workflows, not just short question answering.

The examples below are meant to show the shape of the benchmark. They are illustrative of the work being tested, not a review of every individual case.

Environment mix

Where the suite runs and what it depends on

The suite intentionally mixes local, mocked, and real prerequisites so reviewers can tell model misses apart from infrastructure gaps.

Feasibility mix

  • mock43

    Uses seeded or mocked services so the task shape stays realistic without depending on live external accounts.

  • local35

    Runs entirely inside the local harness and file-backed workspace.

  • real15

    Depends on real external surfaces and therefore carries more operational risk when prerequisites are missing.

Connector tier mix

  • Tier 135

    Primarily local harness behavior with minimal external dependency.

  • Tier 243

    Connector-style workflows that are central to the current benchmark release shape.

  • Tier 315

    Higher-dependency cases that lean on real integrations or heavier prerequisites.

Case construction

How cases are grounded and why that matters

Some cases check saved state, some inspect generated artifacts, and some script follow-up turns. These choices affect how strongly a result is grounded.

Grounding and follow-up structure

  • Cases with saved-state checks18

    These cases verify something concrete changed in the workspace or persisted state.

  • Cases with artifact checks24

    These cases inspect generated files or structured outputs instead of only reading the final reply.

  • Cases with response-fact checks23

    These cases require specific facts to appear in the final answer so the reply is grounded in the task output.

  • Cases with scripted extra turns6

    These cases simulate the follow-up or confirmation turns a real user would need to provide.

  • Cases with an explicit clarification policy6

    These cases define when the harness is allowed to answer a clarification request instead of leaving it ambiguous.

  • Cases seeded with prior messages6

    These cases start with existing context so the benchmark can measure memory and follow-through, not only first-turn behavior.

Notes for readers

  • The suite mixes local, mocked, and real prerequisites so reviewers can separate model behavior from missing infrastructure.
  • Category counts describe workload shape only; they do not automatically imply that every category is equally difficult.
  • The workbook is meant for auditing and debugging. The homepage is the reading layer, and the workbook is the evidence layer behind it.
