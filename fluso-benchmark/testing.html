Testing

How the benchmark tries to stay fair

This benchmark compares models only when the setup is held constant: same case universe, same scoring profile, same connector tier, and the same fixed judge.

Completion over eloquence

The benchmark rewards finishing the task cleanly. A model that did useful work but still asked for unnecessary confirmation can still lose the case.

Tools matter

Many tasks require actual connector or file-system execution. The suite is meant to catch the difference between plausible prose and grounded results.

Invalid runs stay out

Runs with contamination or fairness drift do not enter the main leaderboard. They can still be reviewed separately, but they are not allowed to influence the headline comparison.

Reading

How to interpret the results

The right reading order is leaderboard first, task-family shape second, then cost and failure pattern.

  • 1. Start with the clean leaderboard

    This answers the simple question: which models finished more tasks under the same benchmark conditions?

  • 2. Look at task-family shape

    Overall scores can hide strong specialization. The heatmap shows whether a model is better at connectors, memory, observability, or longer multi-step work.

  • 3. Use cost and failure mix to qualify the story

    If two models are close on completion but very different in cost, latency, or failure mode, that changes the real-world interpretation.
